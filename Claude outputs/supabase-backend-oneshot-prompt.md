# One-shot prompt — paste into Cursor / Claude Code in the Dashboard repo root

Give real backend + auth to the VBSPU Dashboard (Next.js 16 app router, TS, Tailwind). Currently all data is in-memory (`data/store.ts`/`globalStore.ts`, reset on restart) + demo cookie auth (`lib/demo-accounts.ts`, unsigned `"<userId>|<role>"` cookie, checked in `middleware.ts`). Replace this with Supabase (Postgres + Auth) while keeping the existing Excel pipeline as a second data source. Act directly, no confirmation prompts, minimize back-and-forth — do the whole thing in one pass.

## 0. Context already in repo — reuse, don't rebuild
- `supabase/schema.sql` + `supabase/seed.sql` already exist, regenerated by `scripts/import-excel-data.ts` → `scripts/split-departments.ts` (chained as `npm run import:excel`). They already model departments, programs, faculty, `faculty_departments` join table, infrastructure, hod_submissions, faculty_research, faculty_projects, faculty_targets. Extend this schema, don't replace it.
- Roles: `vc`, `registrar`, `hod`, `faculty`, `et`, `admin` (`components/roles.ts`, `data/types.ts`). Faculty can belong to multiple departments (`departments: string[]`, `primaryDepartment`).
- Mutations already funnel through one file: `lib/data/faculty.ts` (`createFaculty`, stubbed `updateFaculty`/`deleteFaculty`) and `lib/actions.ts` (server actions, `requireUser(roles)` guard). Keep this pattern — every table gets one `lib/data/<entity>.ts` module as its only write path.
- Approval workflow already modeled: `ChangeRequest` (`data/types.ts`) — `edit`/`onboarding`, reviewed only by `admin` today (`lib/actions.ts: adminApprove/adminReject`, `app/admin/approvals/page.tsx`). Keep this table and its single-approver-is-admin behavior; don't invent a multi-tier approval chain unless asked.
- Excel-imported data lives in `data/imported/*.json` — treat as read-only, versioned snapshots refreshed by `npm run import:excel` whenever new spreadsheets come in from Drive.

## 1. Supabase project
- Create tables per `supabase/schema.sql`, plus new ones:
  - `profiles` — `id uuid references auth.users primary key`, `role text check (role in ('vc','registrar','hod','faculty','et','admin'))`, `dept_id text references departments(id)` (nullable), `faculty_id text references faculty(id)` (nullable), `display_name text`.
  - Keep `change_requests` mirroring the `ChangeRequest` interface exactly (same field names, snake_case).
- Enable RLS on every table. Policies:
  - `faculty`: faculty role reads/updates only rows matching their own `faculty_id`; hod/registrar/vc/admin/et read all; only admin (service role, via server action) writes directly — everyone else writes through a `change_requests` insert.
  - `change_requests`: any authenticated user can insert their own (`submitted_by_user_id = auth.uid()`); only admin role can update status (approve/reject); submitter + admin can select their own/all respectively.
  - Read-mostly tables (`departments`, `programs`, `infrastructure`, etc.): all authenticated roles read; writes go through server actions using the service-role key, never client-side.

## 2. Auth — one real login per person
- Use Supabase Auth (email + password), not the demo cookie system.
- Write `scripts/create-logins.ts`: for every row in `data/imported/faculty.json` (and one account each for vc/registrar/et/admin, one per HoD per department), call `supabase.auth.admin.createUser` with a generated temp password, then insert the matching `profiles` row (role, dept_id/faculty_id, display_name). Output a CSV `credentials-export.csv` (email, temp password, role, name) — gitignore this file, never commit it.
- Faculty email: use `email` field from the faculty record if present, else `<slugified-name>@vbspu.local` placeholder — flag placeholders in the CSV so real emails can be swapped in later.
- Replace `lib/session.ts` to read the Supabase session (via `@supabase/ssr`) instead of the demo cookie; `getSessionUser`/`getSessionRole` now join `auth.users` → `profiles`.
- Update `middleware.ts` to use the Supabase SSR middleware client for session refresh + route protection, keeping the existing per-role path guards.
- Keep `lib/demo-accounts.ts` only as a fallback for local dev without Supabase env vars configured (feature-flag it off in production).

## 3. Hybrid data layer (Supabase + Excel JSON)
- Every `data/data/<entity>.ts` read function: try Supabase first; if the query returns no matching row (not yet migrated/seeded), fall back to reading `data/imported/<entity>.json`. Merge, don't duplicate — Supabase rows win when both exist (match on `id`).
- All writes (`createFaculty`, `updateFaculty`, `approveChangeRequest`, etc.) go to Supabase only. Never write back to the JSON files at runtime — those are only refreshed by re-running `npm run import:excel` against new spreadsheets.
- Add `scripts/seed-supabase.ts`: reads `data/imported/*.json`, upserts into Supabase tables (departments → programs → faculty → faculty_departments → the rest), idempotent on `id`. Run this after every `npm run import:excel` to keep Supabase in sync with refreshed spreadsheets.
